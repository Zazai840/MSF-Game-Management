# Running Zone

The MSF Olympics Running Zone app. Children are identified only by wristband number; joined helpers use their own first names.

## Run locally

Install Docker with Compose. Copy `.env.example` to `.env`, choose an owner password and a database password, and put the URL-encoded database password in `DATABASE_URL`. Keep `.env` private; it is ignored by Git. The database hostname inside Compose is `database`.

Start the app and persistent Postgres database with one command:

```sh
docker compose up --build
```

Open http://localhost:3000. When no Olympics day exists, join with the owner password and your first name. This starts the day as a scoring team member. Open Lead → Day to read the day code for volunteers and the lead code. Later joins use the day code and an unused first name. The phone stays joined through reloads.

`docker compose down` stops the app and keeps the day's data. `APP_PORT` and `DATABASE_PORT` in `.env` can change the default host ports (3000 and 5433). Rebuilding does not clear the day. The database password must match the value used to initialise the persistent database volume.

For fast development, install Node.js 22.12+ and Postgres, run `npm ci`, then provide `DATABASE_URL` and `OWNER_PASSWORD` as environment settings and run `npm run dev`. The server serves the API and Vite screens together at port 3000; `HOST` and `PORT` are optional. For a production build, run `npm run build`, then `NODE_ENV=production npm start` with those same required settings. There is no default owner password or application database connection.

The Day tab starts with the 20 individual events from the scoring template. Scoring team members can rename events, add an event with its section and event format, and switch events off or back on. Confirm the event list after checking it; any setup change asks you to confirm again. Switched-off events remain visible on Day and are omitted from volunteer event choices.

Start line lists races already checked in, then lets a helper choose an event and section for a new race. Enter wristband numbers using the keypad and Next, tap a number to remove it, then choose That's everyone and check the list before Save. The server allocates Heat or Race numbers. Saved races can be corrected or deleted before finishing order is recorded. A failed save keeps the entry and its original version, including across reloads; no background save or retry occurs. Each draft belongs to its joined phone and Olympics day.

Numbers outside the known ranges, from another section, or already in another active race of the same event show amber warnings. Choose Fix number to return to the keypad or Keep to continue without lead approval or a comment. Kept warnings stay on the runner's entry and appear on the check screen; they never refuse a race. Either Beaver section accepts 1–999. Deleted races do not cause an already-ran warning.

Finish order opens the oldest waiting race. Tap a number for each place, or tap the places trail to go back. Add a missing runner with the same keypad and Fix/Keep warnings. Nobody else crossed the line asks whether each remaining runner did not finish or didn't run. Check the order, use the arrows to rearrange, then Save. Other race shows waiting and recently saved races for correction. Each job keeps an unsaved draft across refreshes and reloads, with its original versions; another phone's changes must be opened explicitly before saving again.

Times opens on the oldest waiting race and can be recorded before Finish order. Type digits only: 1234 displays 12.34 and 13240 displays 1:32.40. Next and Back move between places; the first digit in a reopened place replaces its time. No more finishers marks the remaining slots, and the check screen can undo the first No finisher. Fix time or Keep handles a later place that is faster. A finish-count disagreement appears prominently and returns the race to the top of Times. Finals never need times. Empty races and races with no finishers can save their empty or No finisher times record.

The Lead area's Results tab groups the programme by event name. Open an event for its provisional leaderboard: heats highlight eight and mark six Q; timed events highlight six and mark the first three medal places. Only fully recorded races with matching finisher counts and ordered times rank. Did not finish rows sit at the bottom, warnings retain their wording in amber, and a wristband used in two active races appears in both with Ran twice. Not ranked yet explains incomplete races. Results refresh every five seconds while visible and offer manual refresh.

Leads can tap a runner in Results to disqualify them, choosing a reason, or lift a disqualification. Other and lifting require a comment. The ranking updates immediately; the child remains visible at the bottom with the reason. A note tag marks touched rows, the event list shows the latest note time, and Audit notes below the leaderboard retain the joined name, time, action and comment, newest first.

## Check changes

```sh
npm ci
npm run verify
npx playwright install chromium
npm run test:e2e
```

The default test database connection is local Postgres on port 5432 using your operating-system username. Set `PG_ADMIN_URL` to a Postgres connection with database-creation permission if yours differs. If using the Compose database from the host, it is `postgresql://running:YOUR_URL_ENCODED_DATABASE_PASSWORD@localhost:5433/postgres`.

`npm test` creates a fresh process-specific Postgres database, runs HTTP API tests in-process against it and plain results-rule unit tests, then drops that generated database. Different worktrees can run tests concurrently. `TEST_DATABASE_URL` or `TEST_DATABASE_NAME` selects a retained test database; only names matching `msf_spec22_<digits>_test` or `msf_spec22_<digits>_e2e` may be cleared. Never use an application database for tests. Test files run sequentially because each HTTP test resets its isolated day's state.

Playwright builds and starts a production app on port 4323 with a fresh, isolated database and runs at iPhone, Android and desktop viewport sizes. Override `E2E_PORT` for concurrent browser runs; optional `E2E_DATABASE_URL` / `E2E_DATABASE_NAME` select a dedicated test database. Browser databases are retained after the run for inspection. Phone sizes use Chromium; real Safari and Samsung Internet checks belong to the rehearsal. Screenshots and failed traces appear in ignored `test-results/`.

The build measures all statically imported first-load JavaScript after gzip and fails above 100,000 bytes. The Lead screen is a dynamic import and is fetched only when an authorised phone opens it. No component library or CSS framework is used.

Production builds install an app-shell service worker on HTTPS (or localhost). It caches only the volunteer HTML, JavaScript and CSS, so reopening is quick; race reads and saves always need the server. Lead is fetched only when opened and is not pre-cached. A new deploy shows **New version, tap to reload** and waits for that tap; unfinished job entries survive the reload. The browser checks for updates when the phone becomes visible or focused and once a minute while visible. Development does not install the worker. The first-load budget includes the worker and the old-browser bootstrap; older phones get a plain message before the application opens.

## Module boundaries

- `createApp(settings)` opens Postgres and returns a Fastify instance for HTTP tests or the web server. Settings hold the database URL and owner password. `resetTestDay` is restricted to isolated test database names.
- Register authenticated HTTP actions through `actions(app, pool)(method, path, minimumLevel, handler)`. It authenticates the phone and enforces the shared Volunteer → Lead → Scoring team ladder before calling the handler. Domain refusals use `Refusal(status, message)`.
- `GET /api/me` returns `{id, name, level}`. `POST /api/join` accepts `{code, name}` and returns `{token, phone}`. `POST /api/become-lead` accepts `{code}`. Tokens are random, stored as hashes on the server and held in browser storage on the phone.
- `GET /api/home` returns the phone and job waiting counts, plus `needsYou` only for leads. `GET /api/lead` requires Lead; `GET /api/day` requires Scoring team and returns the codes.
- Scoring team manages joined phones at `GET /api/day/phones` (names, levels, day-level audit notes). `POST /api/day/phones/:phoneId/remove` revokes a token; `POST /api/day/phones/:phoneId/scoring-team` accepts `{scoringTeam:true|false}` to promote a joined lead or return scoring team to Lead. `POST /api/day/day-code` makes a distinct new day code while retaining joined phones; `/api/day/lead-code` makes a distinct new lead code and demotes ordinary leads to Volunteer, retaining their jobs. Access and setup mutations share the authenticated day lock, recheck current permissions, and advance the export revision. Joining takes advisory lock 23001 before the day row lock; Start new day must use the same order.
- `GET /api/events` is a volunteer read returning enabled events. Day also returns all events, `eventsConfirmed`, and `revision`. Scoring-team setup actions are `POST /api/day/confirm-events`, `POST /api/day/events` (`code`, `name`, `section`, `format`), `POST /api/day/events/:code/rename` (`name`), and `POST /api/day/events/:code/enabled` (`enabled`). Event IDs remain stable when names change. Setup writes and day revision increments share one transaction; changing the programme clears its confirmation.
- `src/shared/results-rules.ts` exposes `eventResults(EventState)`, the pure results entry point. It takes an event and flat race facts (stable runners, finishing order, place times and deletion) and returns ranked rows, highlights, Q or medal marks, qualifiers, medal places, incomplete-race reasons, provisional status and race count. Typed tie and lead-item outputs are reserved for their later workflows. Keep ranking logic here rather than in HTTP handlers or screens.
- `src/client/api.ts` is the browser HTTP boundary and clears this app's saved browser data when a phone is refused as removed. `App.tsx` polls the home read every five seconds and refreshes when the screen becomes visible. The Lead screen polls its own read.
- `GET /api/jobs/start-line` returns the confirmed enabled programme, oldest waiting races and recent races. `POST /api/races/check-in` accepts `eventCode`, numeric `runners` and an optional `requestId` identifying a retry of the same new check-in. `GET /api/races/:id` returns the race. `POST /api/races/:id/runners` accepts `baseVersion` and numeric `runners`; `POST /api/races/:id/delete` accepts boolean `permanent`. These actions all require Volunteer and scope every race to the authenticated phone's day. They return `status: saved` only after their transaction commits.
- `RaceRead` has stable runner IDs and independently versioned `runners`, `finish` and `times` parts; a null value means a part has not been recorded. Changes update the day revision atomically. The counter for each event and kind survives race deletion, so numbers are never reused. Deleted races are retained with their parts but excluded from active job reads and waiting counts. Start-line edits and deletion refuse a recorded finishing order; later lead rulings use their own audited commands.
- `src/shared/wristband-checks.ts` exposes pure `sectionForWristband` and `wristbandWarnings` checks and the shared runner-list refusals. Checks take one event's race numbers, ignore deleted/current races, and can skip the already-ran check for pre-filled finals and re-runs. `POST /api/wristband-check` accepts `eventCode`, `wristband` and optional current `raceId`, returning plain warnings to any joined phone. Check-in and runner-list saves optionally accept `keptWarnings` as wristband numbers; the server computes warning messages and stores `{kind, message, kept}` on each runner. Unchanged entries retain their warnings when other runners are edited.

- `GET /api/jobs/finish-order` returns oldest `waiting` races and saved `recent` races. `POST /api/races/:id/finish` accepts `baseVersion` (finish part), `runnersVersion`, numeric `order`, `didNotFinish`, `didNotRun`, `added`, and optional `keptWarnings`. It saves `FinishingOrder {order: entryId[], didNotFinish: entryId[]}`. Added entries carry `addedAtFinish: true`; didn't-run entries are removed from the runner part. An addition or removal increments the runners version in the same transaction. Simple place corrections touch only the finish version, leaving Times independent for later pairing by place. All joined levels use this same Volunteer action.

- `src/shared/time-entry.ts` provides pure digit parsing, typed and stored formatting, and out-of-order checks. `RaceTimes` stores `{places: (number | null)[], outOfOrder: boolean}`; null means No finisher and is allowed only as a suffix. `GET /api/jobs/times` returns waiting races with count disagreements first and recently timed races. `POST /api/races/:id/times` accepts `baseVersion` and `places` as whole hundredths or nulls, returns the committed race, and refuses stale times or finals. It trims surplus trailing nulls after a runner is removed; surplus numeric times or missing slots ask the helper to reopen the race. Times writes leave other part versions unchanged.
- `RaceRead.recording`, derived by `src/shared/recording.ts`, contains the count disagreement message, `readyForRanking`, and each entry's current place and time. Places in `FinishingOrder` point to stable entries; `RaceTimes` points to places, so correcting either part re-pairs automatically. Out-of-order times and mismatched counts are saved but keep a race unranked. Old trailing No finisher capacity has no effect on readiness.

- `GET /api/lead/results` returns `ResultsRead` (confirmation and ordered event-name groups with event summaries). `GET /api/lead/events/:code/results` returns `EventResultsRead` (event and the pure rules output). Both require Lead and read a consistent database snapshot scoped to the phone's Olympics day. `src/server/results/read.ts` is the storage adapter into `EventState`; later rulings can recompute results through this same adapter inside their transaction. Results display ships with the dynamically loaded Lead bundle.

- Lead rulings use `rulingChange(pool, phone, callback, minimumLevel)` in `src/server/rulings/records.ts`: the authenticated day lock rechecks current membership and level, commits the change and export revision together. `writeAuditNote` accepts an event ID (or null for a day note), snapshot prose and stable touched entry IDs. `readRulings` / `readAuditNotes` load facts; `rulingDetails` validates optional or required comments. Audit actor names and prose survive phone removal.
- `POST /api/lead/races/:raceId/runners/:entryId/disqualify` accepts `reason` and optional `comment`; Other requires it. `POST .../lift-disqualification` requires `comment`. Both require Lead, retain stable runner identities, append an audit note and return recomputed `EventResultsRead`. Disqualifications are independent of job versions and work for any stored race kind. `EventState.rulings` and `auditNotes` drive exclusion and note tags in the pure results rules.
