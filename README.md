# Running Zone

The MSF Olympics Running Zone app. Children are identified only by wristband number; helpers sign in with a profile in their own full name.

## Run locally

Install Docker with Compose. Copy `.env.example` to `.env`, choose an owner password and a database password, and put the URL-encoded database password in `DATABASE_URL`. Keep `.env` private; it is ignored by Git. The database hostname inside Compose is `database`.

Start the app and persistent Postgres database with one command:

```sh
docker compose up --build
```

Open http://localhost:3000. Type the owner password where the Olympics password goes, then your full name. With no Olympics day running this starts the first day and makes the Olympics password; you sign in as the scoring team. Read the Olympics password and the lead code from Dashboard → Day setup. Volunteers type the Olympics password once per phone, then create a profile with an unused full name or tap their name. The phone stays signed in through reloads. The database must start empty for this version: drop a local database made before it.

`docker compose down` stops the app and keeps the day's data. `APP_PORT` and `DATABASE_PORT` in `.env` can change the default host ports (3000 and 5433). Rebuilding does not clear the day. The database password must match the value used to initialise the persistent database volume.

For fast development, install Node.js 22.12+ and Postgres, run `npm ci`, then provide `DATABASE_URL` and `OWNER_PASSWORD` as environment settings and run `npm run dev`. The server serves the API and Vite screens together at port 3000; `HOST` and `PORT` are optional. Behind a reverse proxy, set `TRUSTED_PROXY_HOPS` to the number of proxies in front of the server (usually 1) so wrong-code backoff tells phones apart; leave it unset when phones reach the server directly. For a production build, run `npm run build`, then `NODE_ENV=production npm start` with those same required settings. There is no default owner password or application database connection.

Set `TEST_BUILD=1` only on a public test deployment. The shared header then shows **Test build · <short commit>** and a **Report a bug** link that opens the tester bug form (`.github/ISSUE_TEMPLATE/tester-bug.yml`) pre-filled with the commit and the current screen. The commit comes from Railway's `RAILWAY_GIT_COMMIT_SHA` and shows as `unknown` when that is absent. Without `TEST_BUILD`, nothing extra shows.

Dashboard → Day setup → Events starts with the 20 individual events from the scoring template. Scoring team members can rename events, add an event with its section and event format, and switch events off or back on. Confirm the event list after checking it; any setup change asks you to confirm again. Switched-off events remain visible on Events and are omitted from volunteer event choices.

Check in runners (the Start line job) lists races already checked in, then lets a helper choose an event and section for a new race. Type each wristband number on the phone's own number pad and tap Next (or press Enter), tap a number to remove it, then choose That's everyone and check the list before Save. The server allocates Heat or Race numbers. Saved races can be corrected or deleted before finishing order is recorded. A failed save keeps the entry and its original version, including across reloads; no background save or retry occurs. Each draft belongs to its signed-in phone and Olympics day.

Numbers outside the known ranges, from another section, or already in another active race of the same event show amber warnings. Choose Fix number to retype it or Keep to continue without lead approval or a comment. Kept warnings stay on the runner's entry and appear on the check screen; they never refuse a race. Either Beaver section accepts 1–999. Deleted races do not cause an already-ran warning.

Record the finishing order (the Finish order job) starts with the race picker: waiting races, oldest first, then recently saved races. Tap a runner for each place, or tap the places trail to go back. Add a missing runner with + Runner not on the list, typed on the number pad with the same Fix/Keep warnings. Nobody else crossed the line asks whether each remaining runner did not finish or didn't run. Check the order, drag the handle on the right to move a runner, then Save. Tapping the job or race name in the trail at the top goes back to the race picker, where a saved race can be reopened for correction. Each job keeps an unsaved draft across refreshes and reloads, with its original versions; a different save from another phone is kept alongside for a lead to choose. The helper can finish saving their own draft.

Enter times (the Times job) starts with the same race picker and can be recorded before Finish order. Type digits only: 1234 displays 12.34 and 13240 displays 1:32.40. Next and Back move between places; the first digit in a reopened place replaces its time. No more finishers marks the remaining slots, and the check screen can undo the first No finisher. Fix time or Keep handles a later place that is faster. A finish-count disagreement appears prominently and returns the race to the top of Times. Finals never need times. Empty races and races with no finishers can save their empty or No finisher times record.

Dashboard → Results groups the programme by event name. Open an event for its provisional leaderboard: heats highlight eight and mark six Q; timed events highlight six and mark the first three medal places. Only fully recorded races with matching finisher counts and ordered times rank. Did not finish rows sit at the bottom, warnings retain their wording in amber, and a wristband used in two active races appears in both with Ran twice. Not ranked yet explains incomplete races. Results refresh every five seconds while visible and offer manual refresh.

Leads can tap a runner in Results to disqualify them, choosing a reason, or lift a disqualification. Other and lifting require a comment. The ranking updates immediately; the child remains visible at the bottom with the reason. A note tag marks touched rows, the event list shows the latest note time, and Audit notes below the leaderboard retain the signed-in name, time, action and comment, newest first.

Scoring team members can download the whole Olympics day from Dashboard → Day setup → Download day export, including incomplete and deleted races. The workbook has Input - Running (completed events, winners in J/M/P with formula columns blank), Finals (original seeds, absences, call-ups and final positions), All results, and Audit notes. Times are numeric seconds to two decimal places; audit times are UTC. Day setup shows the last export time and whether later changes need another download.

## Test build on Railway

The public test build runs `main` on Railway's free plan as two services in one project: the app service, built from this repo's `Dockerfile`, and a Railway PostgreSQL service. The app is served at the HTTPS domain Railway generates (ending `.up.railway.app`). `railway.json` sets the Dockerfile build, the `/api/health` health check and restart on failure. Railway supplies `PORT`; the image already listens on all interfaces.

Set these variables on the app service. Never write their values in GitHub, the repo or an issue.

| Variable | What it holds |
| --- | --- |
| `DATABASE_URL` | A reference to the Postgres service's connection URL (`${{Postgres.DATABASE_URL}}`), never a typed password |
| `OWNER_PASSWORD` | The owner password, 24 or more random characters, kept in the owner's password manager |
| `TRUSTED_PROXY_HOPS` | The number of proxies in front of the server (Railway: 1, confirmed from the request logs) |
| `TEST_BUILD` | Marks the deployment as a test build so phones show the build's commit and a bug-report link; set to `1` |

Railway sets `RAILWAY_GIT_COMMIT_SHA` itself; the test build marker reads it.

`TRUSTED_PROXY_HOPS` is safe only when every request passes through the proxy, so leave it unset wherever phones can reach the server directly.

Every push to `main` builds and deploys a new version. Railway switches traffic only after the new version answers `/api/health`, so a failing build or health check keeps the previous version running. Look at the deployment's build and runtime logs in the Railway dashboard.

To clear the Olympics day between test sessions, use the normal Start new day flow on Dashboard → Day setup: download the day export, then type **NEW DAY**. Redeploying never clears the day; the data lives in the Postgres service.

To onboard testers, sign in first with the owner password, then send testers the Railway domain and the Olympics password from Day setup (and the lead code only to testers who should try Lead). They type the Olympics password and create a profile with their own full name. Testers report bugs with the **Report a bug** link in the app header, which opens a GitHub issue with the commit and screen filled in.

### Smoke check against the deployed build

`npm run test:remote` checks that the deployed build works for 5 testers: it signs in the owner and 4 volunteers, runs one 60m Girl Cubs (R4) race through check-in, finishing order and times, shows a mistyped Olympics password on one phone does not block another, checks the Test build marker, downloads the day export, and makes 70 saves across the 5 phones with no refusal or server error. It uses `playwright.remote.config.ts` (no local server, no test database) and skips unless `REMOTE_BASE_URL` and `REMOTE_OWNER_PASSWORD` are set. It never clears the day: it adds 5 profiles named `Smoke ...` and one R4 race to it, so clear the day afterwards if testers should start fresh.

```sh
REMOTE_BASE_URL=https://YOUR-DOMAIN.up.railway.app REMOTE_OWNER_PASSWORD='...' npm run test:remote
```

The owner password signs in on a running day, or starts the day when none exists. Each run uses one of the 5 wrong passwords allowed per address in 15 minutes, so wait 15 minutes after 4 runs.

### Guide for testers

- **The link:** open the Railway domain the owner sends you (it ends `.up.railway.app`) on your phone.
- **Signing in:** the owner shares the Olympics password with you directly. Type it once, then create a profile with your own full name. Next time, tap your name. Only testers trying Lead get the lead code.
- **Reporting a bug:** tap **Report a bug** in the header on the screen where it happened. It opens a GitHub issue with the build's commit and the screen already filled in; say what happened and what you expected.
- **Data may be cleared:** this is a test build. The owner clears the day between test sessions, so anything you enter can disappear.

## Check changes

```sh
npm ci
npm run verify
npx playwright install chromium
npm run test:e2e
```

The default test database connection is local Postgres on port 5432 using your operating-system username. Set `PG_ADMIN_URL` to a Postgres connection with database-creation permission if yours differs. If using the Compose database from the host, it is `postgresql://running:YOUR_URL_ENCODED_DATABASE_PASSWORD@localhost:5433/postgres`.

`npm test` creates a fresh process-specific Postgres database, runs HTTP API tests in-process against it and plain results-rule unit tests, then drops that generated database. Different worktrees can run tests concurrently. `TEST_DATABASE_URL` or `TEST_DATABASE_NAME` selects a retained test database; only names matching `msf_spec22_<digits>_test` or `msf_spec22_<digits>_e2e` may be cleared. Never use an application database for tests. Test files run sequentially because each HTTP test resets its isolated day's state.

Playwright builds and starts a production app on port 4323 with a fresh, isolated database and runs at iPhone, Android and desktop viewport sizes. Override `E2E_PORT` for concurrent browser runs; optional `E2E_DATABASE_URL` / `E2E_DATABASE_NAME` select a dedicated test database. Browser databases are retained after the run for inspection. Phone sizes use Chromium; real Safari and Samsung Internet checks belong to the rehearsal. `npm run test:e2e` then makes a second run, of the test build marker spec in `e2e/test-build/`, against a server started with `TEST_BUILD=1` (`playwright.test-build.config.ts`). Screenshots and failed traces appear in ignored `test-results/`.

The build measures the volunteer first load (all statically imported JavaScript and CSS, the self-hosted Nunito font files and the service worker) after gzip, prints the total and fails above 1,500,000 bytes (the aim is about 1 MB). The Lead screen is a dynamic import and is fetched only when an authorised phone opens it. No component library or CSS framework is used; colour tokens and shared styles live in `src/client/theme.css`.

Production builds install an app-shell service worker on HTTPS (or localhost). It caches only the volunteer HTML, JavaScript and CSS, so reopening is quick; race reads and saves always need the server. Lead is fetched only when opened and is not pre-cached. Every build has its own id, which the server sends on every response (`x-build-id`) and in every live snapshot (`build`). A phone that sees another build's id updates the worker and reloads at once, with no tap; a new worker activates itself, and a failed load of Lead reloads the app too. Unfinished job entries survive the reload; the race screen keeps no copy on the phone, so at most an entry in flight is retyped. Development does not install the worker. The first-load budget includes the worker and the old-browser bootstrap; older phones get a plain message before the application opens.

## Module boundaries

- `createApp(settings)` opens Postgres and returns a Fastify instance for HTTP tests or the web server. Settings hold the database URL and owner password. `resetTestDay` is restricted to isolated test database names.
- Register authenticated HTTP actions through `actions(app, pool)(method, path, minimumLevel, handler)`. It authenticates the phone and enforces the shared Volunteer → Lead → Scoring team ladder before calling the handler. Domain refusals use `Refusal(status, message)`.
- `POST /api/password` accepts `{password}`: the Olympics password returns `{kind:'olympics', pass}`, the owner password `{kind:'owner', dayRunning}`; wrong passwords back off per IP. The pass is bound to the password's version, so changing the password invalidates every pass. `POST /api/owner-sign-in` accepts `{password, name, profiles}` (the phone's `{id, secret}` pairs), starts the first day if none is running (never restarting one), and signs in as Scoring team marked as owner; a name taken by a profile on another phone gets the lowest free number from 2. `POST /api/profiles` accepts `{pass, name}`, creates a profile and signs it in as Volunteer, refusing a taken name with `taken:true`. `POST /api/sign-in` accepts `{pass, profileId, secret}`; today's sign-in keeps its role. `POST /api/lead-sign-in` accepts `{pass, name, code, profiles}` and signs in as Lead with today's lead code; like owner sign-in it never refuses a name, numbering one taken on another phone, and wrong codes back off per held profile and IP. Each returns `{token, phone}` (plus `pass` and `profile` with its `secret` when newly made). `POST /api/phone-profiles` accepts `{pass, profiles}` and returns today's role for each profile the phone holds as `{id, level}`, or `{id, moved:true}` for one moved away by That's me. `POST /api/sign-out` (Volunteer) ends this phone's session and clears its holds; its profiles stay on the phone. A 401 carries a `reason` so the phone clears exactly what it calls for: `signed-out` (signed out or removed), `moved` (the profile went to another phone by That's me), `password-changed` (the Olympics password changed, or the pass is missing or old) and `new-day` (Start new day ended the session); a token nobody knows has no reason and the phone clears everything. `GET /api/me` returns `{id, dayId, name, level, profileId}`: `id` is today's sign-in row, which race parts name as their author. `POST /api/become-lead` accepts `{code}`. Tokens are random, stored as hashes on the server and held in browser storage on the phone.
- `GET /api/home` returns the phone, the switched-on `events` in programme order (`{code, name, section, race:{kind, number}}`, the race being each event's current race) and job waiting counts, plus `needsYou` only for leads. `GET /api/lead` requires Lead; `GET /api/day` requires Scoring team and returns the lead code and the Olympics password.
- That's me: `POST /api/thats-me` accepts `{pass, name}` for a profile held on another phone and returns `{id, name, secret}`. The waiting phone polls `POST /api/thats-me/status` with `{pass, secret}`, getting `{status}` (`waiting`, `declined` or `cancelled`) until a lead decides; the approved answer, `{status:'approved', profile, token, phone}`, is handed out once, and later reads are refused as no longer waiting. `POST /api/thats-me/cancel` accepts `{secret}`. Waiting requests appear as `profileRequests` in `GET /api/lead`; `POST /api/lead/thats-me/:requestId/approve` and `.../decline` require Lead and write a day-level audit note. Approving gives the profile the waiting phone's secret, so the old phone is refused with reason `moved`.
- Scoring team manages signed-in phones at `GET /api/day/phones` (names, levels, owner marker, day-level audit notes). `POST /api/day/phones/:phoneId/role` accepts `{role}` (`Volunteer`, `Lead` or `Scoring team`) for today; nobody changes their own role or lowers the owner's. `POST /api/day/phones/:phoneId/remove` signs that phone out with reason `signed-out` and makes the row a volunteer again, except the owner's, which keeps Scoring team. `POST /api/day/olympics-password` accepts `{password}` (at least 6 characters, different from the current one) and ends every session, the caller's too, with reason `password-changed`; roles stay on today's rows. `POST /api/day/lead-code` makes a distinct new lead code and demotes ordinary leads to Volunteer, retaining their jobs. Access and setup mutations share the authenticated day lock, recheck current permissions, and advance the export revision. Every sign-in takes advisory lock 23001 before the day row lock; Start new day must use the same order.
- `GET /api/events` is a volunteer read returning enabled events. Day also returns all events, `eventsConfirmed`, and `revision`. Scoring-team setup actions are `POST /api/day/confirm-events`, `POST /api/day/events` (`code`, `name`, `section`, `format`), `POST /api/day/events/:code/rename` (`name`), and `POST /api/day/events/:code/enabled` (`enabled`). Event IDs remain stable when names change. Setup writes and day revision increments share one transaction; changing the programme clears its confirmation.
- `src/shared/results-rules.ts` exposes `eventResults(EventState)`, the pure results entry point. It takes an event and flat race facts (stable runners, finishing order, place times and deletion) and returns ranked rows, highlights, Q or medal marks, qualifiers, medal places, incomplete-race reasons, provisional status and race count. Typed tie and lead-item outputs are reserved for their later workflows. Keep ranking logic here rather than in HTTP handlers or screens.
- Live streams (Server-Sent Events, `src/server/live/routes.ts`): `GET /api/live/race-screen/:code` (Volunteer) streams one event's race screen as whole `RaceScreenRead` snapshots `{revision, event, race, stageComplete, holds}`, where `race` is the event's current race: its latest stored race that does not count yet, or else the next heat or race (`id: null`, empty parts), not stored until its first check-in; once heats are complete it is the final. Each snapshot is versioned by the day revision, sent first on every connect and again after every committed change that raises it (`dayChanged` in `src/server/live/changes.ts`, called by `raceChange` and Start new day). A `: hb` comment goes every `streamHeartbeatMs` (default 15 s) and the stream ends at `streamLimitMs` (default 10 min); both are `createApp` settings. Refusals (401, unknown event) answer before the stream starts, and a phone signed out mid-stream has its stream ended so its reconnect is told why. Streams are fed in-process, so the app runs as one instance. Phones read them with `useLive` (`src/client/live.ts`): fetch with the bearer token, ignore older snapshots, reconnect at once after a planned end and with backoff after a failure or 30-45 s of silence, and close while the page is hidden.
- Holds and race screen writes (`src/server/races/race-screen.ts`, all Volunteer): `job_holds` stores at most one signed-in phone per event and job (`check-in`, `order`, `times`; a final has no times), shown in snapshots as `holds: {[job]: {id, name}}` with the sign-in id. `GET /api/race-screen/:code` returns the same snapshot as the stream's first frame. `POST /api/race-screen/:code/hold` `{job}` takes a free job (nothing changes if anyone holds it); `POST .../take-over` `{job}` moves it to this phone with an audit note ("Ali took over check-in from Jo on 60m Girl Cubs Heat 2"); `POST .../check-in` `{raceId, version, runners:[{id?, wristband}], keptWarnings?}` writes the holder's whole wristband list at the runners version it saw (`raceId: null`, `version: 0` on the empty next race, whose first write creates it); an entry sent with its `id` is a fixed number and keeps its entry, so its place in the order follows it, and a runner taken off drops out of the order with later places moving up (the finish version stays). `POST .../order` `{raceId, version, order, didNotFinish, didNotRun, added, keptWarnings?}` writes the order holder's whole column at the finish version it saw: `order`, `didNotFinish` and `didNotRun` are entry ids (Didn't run takes the runner off the race), `added` are wristbands added at the finish (stored with `addedAtFinish`, refused if already in the race); entries check-in has since taken off are dropped, and an empty column stores no finishing order. A final's order stays on the Finish order job for now. Writes refuse in order: signed out, "Stage complete - ask a lead", "A lead deleted Heat 2", "Heat 2 is saved - ask a lead to change it", "Ali took over check-in" (or "the order"), "Not saved - check your entries and enter it again"; writing a job nobody holds takes it. Each answers with the snapshot as it then stands and raises the day revision when it changes anything. Holds are cleared when the phone signs out (itself, removed by the scoring team, or Start new day) and when the event's final is stored.
- `src/client/api.ts` is the browser HTTP boundary and clears this app's saved browser data when a phone is refused as removed. `App.tsx` polls the home read every five seconds and refreshes when the screen becomes visible. The Lead screen polls its own read.
- `GET /api/jobs/start-line` returns the enabled programme, with a nonblocking confirmation reminder, oldest waiting races and recent races. `POST /api/races/check-in` accepts `eventCode`, numeric `runners` and an optional `requestId` identifying a retry of the same new check-in. `GET /api/races/:id` returns the race. `POST /api/races/:id/runners` accepts `baseVersion` and numeric `runners`; `POST /api/races/:id/delete` accepts boolean `permanent`. These actions all require Volunteer and scope every race to the authenticated phone's day. They return `status: saved` only after their transaction commits.
- `RaceRead` has stable runner IDs and independently versioned `runners`, `finish` and `times` parts; a null value means a part has not been recorded. Changes update the day revision atomically. The counter for each event and kind survives race deletion, so numbers are never reused. Deleted races are retained with their parts but excluded from active job reads and waiting counts. Start-line edits and deletion refuse a recorded finishing order; later lead rulings use their own audited commands.
- Every part save includes the version that phone opened. A current-version save is a normal correction; a stale identical answer merges silently, and a stale different answer is retained as a clash. Volunteer jobs keep their original draft versions and show **Two versions - zone lead to check**. A clashing race is excluded from ranking with reason **two versions, lead to check**. `GET /api/lead/races/:id` returns candidate answers, saved author names/times and complete history; volunteers see only clash flags. `POST /api/lead/races/:id/clashes/:part` accepts `{candidateId}`, requires Lead and writes an audit note. Choosing Finish restores its coherent runner snapshot (including added and didn't-run runners), preserving independent place times. Choosing a runner list that omits a placed entry clears Finish for correction.
- `src/server/races/versions.ts` centralizes immutable published-part history and saved candidates. `publishPart` is the publication boundary for intentional lead corrections; `savePart` handles volunteer version comparisons. Call inside the existing race/day transaction. Soft deletion retains history; permanent deletion cascades it.
- `src/shared/wristband-checks.ts` exposes pure `sectionForWristband` and `wristbandWarnings` checks and the shared runner-list refusals. Checks take one event's race numbers, ignore deleted/current races, and can skip the already-ran check for pre-filled finals and re-runs. `POST /api/wristband-check` accepts `eventCode`, `wristband` and optional current `raceId`, returning plain warnings to any signed-in phone. Check-in and runner-list saves optionally accept `keptWarnings` as wristband numbers; the server computes warning messages and stores `{kind, message, kept}` on each runner. Unchanged entries retain their warnings when other runners are edited.

- `GET /api/jobs/finish-order` returns oldest `waiting` races and saved `recent` races. `POST /api/races/:id/finish` accepts `baseVersion` (finish part), `runnersVersion`, numeric `order`, `didNotFinish`, `didNotRun`, `added`, and optional `keptWarnings`. It saves `FinishingOrder {order: entryId[], didNotFinish: entryId[]}`. Added entries carry `addedAtFinish: true`; didn't-run entries are removed from the runner part. An addition or removal increments the runners version in the same transaction. Simple place corrections touch only the finish version, leaving Times independent for later pairing by place. Every role uses this same Volunteer action.

- `src/shared/time-entry.ts` provides pure digit parsing, typed and stored formatting, and out-of-order checks. `RaceTimes` stores `{places: (number | null)[], outOfOrder: boolean}`; null means No finisher and is allowed only as a suffix. `GET /api/jobs/times` returns waiting races with count disagreements first and recently timed races. `POST /api/races/:id/times` accepts `baseVersion` and `places` as whole hundredths or nulls, returns the race with a saved, merged or clash outcome, and refuses finals. It trims surplus trailing nulls after a runner is removed; numeric times and missing slots remain visible as a count disagreement. Times writes leave other part versions unchanged.
- `RaceRead.recording`, derived by `src/shared/recording.ts`, contains the count disagreement message, `readyForRanking`, and each entry's current place and time. Places in `FinishingOrder` point to stable entries; `RaceTimes` points to places, so correcting either part re-pairs automatically. Out-of-order times and mismatched counts are saved but keep a race unranked. Old trailing No finisher capacity has no effect on readiness.

- To check (`needsYou` in the API) is the canonical lead queue for clashes, highlighted ties, open eligibility warnings, repeated counted numbers, unchecked additions at the finish, and unaccepted out-of-order times. Pending races contribute runner issues before they can rank. `GET /api/lead` returns the ordered day-level collection with event/race references and persisted timestamps; the home Dashboard count and event-list counts use the same pure rules. Volunteers receive no queue or count. Every To check item opens its race or action sheet directly.
- `POST /api/lead/races/:raceId/runners/:entryId/mark-added-checked` acknowledges only an added-at-finish entry, requires Lead, writes an audit note and advances revision without changing race part versions. Its historical flag remains grey. Wrong section or age disqualification settles open eligibility warnings; lifting it reopens warnings that were not explicitly checked. Ran-twice is recomputed from counted, non-disqualified preliminary appearances, including pending races; finals progression is separate.
- `GET /api/lead/results` returns `ResultsRead` (confirmation and ordered event-name groups with event summaries). `GET /api/lead/events/:code/results` returns `EventResultsRead` (event and the pure rules output). Both require Lead and read a consistent database snapshot scoped to the phone's Olympics day. `src/server/results/read.ts` is the storage adapter into `EventState`; later rulings can recompute results through this same adapter inside their transaction. Results display ships with the dynamically loaded Lead bundle.

- Lead rulings use `rulingChange(pool, phone, callback, minimumLevel)` in `src/server/rulings/records.ts`: the authenticated day lock rechecks current membership and level, commits the change and export revision together. `writeAuditNote` accepts an event ID (or null for a day note), snapshot prose and stable touched entry IDs. `readRulings` / `readAuditNotes` load facts; `rulingDetails` validates optional or required comments. Audit actor names and prose survive phone removal.
- `POST /api/lead/races/:raceId/runners/:entryId/disqualify` accepts `reason` and optional `comment`; Other requires it. `POST .../lift-disqualification` requires `comment`. Both require Lead, retain stable runner identities, append an audit note and return recomputed `EventResultsRead`. Disqualifications are independent of job versions and work for any stored race kind. `EventState.rulings` and `auditNotes` drive exclusion and note tags in the pure results rules.

- Runner actions also offer Mark checked for open eligibility warnings, Correct number with current Fix/Keep checks, and Choose which result counts for a repeated number. Checked flags remain grey; not-counted entries remain struck through below ranked results. Each action is audited. `POST .../mark-warning-checked` accepts an optional comment; `POST .../correct-number` accepts `expectedWristband`, `wristband`, optional `keepWarnings` and comment; `POST .../count-result` selects that stable entry and excludes other active eligible results of its number in the event. All require Lead and return recomputed results. Number correction increments only the runners part version, preserves entry/finish IDs and place times, clears obsolete warning checks and the corrected entry’s exclusion. `isOpenEligibilityWarning` distinguishes actionable eligibility warnings from ran-twice/history for later lead queues.

Lead race corrections use `/api/lead/races/:id/{times,runners,finish-order,delete,restore,re-run}` and the shared race page. Correct finishing order submits wristbands as `{baseVersion,runnersVersion,order,didNotFinish,didNotRun}` at the exact Finish and runner versions: wristbands move between places while times stay by place, and Didn't run takes the runner off the race. Times explicitly accepted by a lead carry `acceptedByLead`; unchanged volunteer saves retain it, changed times clear it. Runner corrections submit stable `entryId`s, `baseVersion` and `finishVersion`; actual new runners invalidate Finish unless a complete explicit finishing order/Did not finish classification is supplied. Numeric Times remain independent, with mismatches surfaced for checking. Deleted races are available only to leads through `/api/lead/events/:code/deleted-races`; re-runs retain the original deleted record and create a numbered prefilled race. Every command writes an audit note atomically with the day revision.

Day export uses `POST /api/day/export` (Scoring team only), returning a no-store XLSX attachment with `X-Day-Revision` and `X-Exported-At`. The server rechecks current Scoring permission under the day lock, builds all sheets from one revision, then records `exportedAt`/`exportedRevision` without incrementing the day revision. `GET /api/day` exposes those nullable fields; a later meaningful change invalidates their revision equality. `eventResults` supplies `allResults` and retained `finalRecords`, including canonical final medals and historical seed provenance. The workbook library runs only on the server. Client JSON and binary calls share `apiResponse` authentication/error handling.

Start new day is at the bottom of the Scoring team's Day setup. Download the day export after the last change, then type **NEW DAY**. `POST /api/day/start-new` accepts `{confirmation:"NEW DAY"}` and refuses a missing or outdated export, the wrong confirmation, or a phone without current Scoring permission. Signing in, code changes, programme edits, recording and rulings all invalidate the export guard. The reset compares revisions inside its transaction; timestamps are for display. Sign-in and reset take advisory lock 23001 before the captured day row and current phone, so a queued sign-in lands on the replacement day.

The reset clears the old day's races, rulings, histories, audit notes, custom events and sign-ins, and seeds the 20 built-in events with confirmation still needed. It keeps only the initiating phone's token, name and Scoring level, and immediately shows its fresh lead code. Profiles and the Olympics password are kept. Everyone else returns to their phone's profile screen on their next request and taps their name to sign in to the new day. Old job drafts are cleared. If the reset committed but its reply was lost, an ordinary Home refresh discovers the new day identity and reopens Day with the fresh lead code. Retrying reset is refused until that new day has a current export.

The browser captures a session generation for every JSON and binary request and checks it again after reading the body. Signing in, removal and a retained-token day switch invalidate older responses before they can clear a newer phone, publish old results, write a draft or replace a token. Starting reset invalidates pending responses before sending and pauses other API dispatches until its outcome, so polling cannot authenticate against the old day during that boundary. A private storage marker also invalidates other tabs sharing the signed-in phone. Home and Lead reads validate the captured day inside their consistent snapshot; they never silently switch an old authenticated request to the replacement day. Browser tests read fresh codes before every test through the original retained scoring token, so actual resets do not depend on test/project ordering.
